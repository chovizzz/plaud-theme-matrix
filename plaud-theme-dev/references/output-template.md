# Path A 输出模板

正文用固定结构，末尾接 `handoff-schema.md` §4 的 yaml 块。结构固定是为了让 QA 能逐项接手——**不要把内容打散进自由段落**。

## 模板

```markdown
## 依赖树

- 来源：<AssessmentRef>（或 InlineLite）
- section / block type：
- render 的 snippets：
- 相关 JS（custom element 及继承链）：
- 相关 CSS（作用域与断点覆盖）：
- schema 选项 / 模板存值：
- 本次新发现（Assess 未覆盖的部分，若有）：

## 根因（Orient）

<机制层根因，一到三句。必须能解释「为什么 A 下坏、B 下好」，并能预测同族出现在哪。>

## 方案（Decide）

**方案 1 — <名字>**：改哪一层 / 影响范围 / 代价 / 风险
**方案 2 — <名字>**：同上
**选择**：<选哪个 + 为什么；与 EntrypointCandidates 风险排序的关系>

（平凡任务写：`Trivial —— 命中平凡判据第 1–6 条，逐条为：…`）

## 同族扫描

<格式见 bug-family-scan.md；bug 修复类必写，其它类型无同族概念时写「不适用（非 bug 修复）」>

## 待 QA 验证的点

- 待验：<…>
- 待验：<…>

## 改动清单（Act）

- `<path>`：<一句话>
- `<path>`：<一句话>

## 顺带发现（不在本次改动内）

改动已就位，待 QA。
```

末尾接 yaml 块。

## 「待 QA 验证的点」怎么写

这是本模板与旧「回归矩阵」的**关键差别**：旧版让实现方自己列回归矩阵，容易滑向"我都跑过了"。现在**验证由 `plaud-theme-qa` 执行，你只负责标明该验什么**。

### 硬规则

1. 每一项以 **「待验：」** 开头。
2. **禁止**出现验证结果词：通过 / 已验证 / 无异常 / 没问题 / 正常 / OK / 全绿。
3. 不写"我在浏览器里看过了"。你没有交付权，也没有验证权。
4. 需要浏览器预览却无法预览的项，仍然照常列为待验项，同时进 `BlockingGaps`。
5. 不要替 QA 下 `NotApplicable` 判定；你只能说"本次未触及 X，建议 QA 视作不适用"，最终判定权在 QA。

### 该覆盖哪些维度（按本次改动实际触及的挑，不是清单照抄）

| 维度 | 何时该列 |
|---|---|
| layout mode / schema 选项 / block type 组合 | 改动受 schema 配置影响时 |
| 空配置 / 满配置双测 | 新增或修改了 schema 字段时 |
| Swiper effect | 任何触及 Swiper 的改动（effect 的必须/禁止约束见 shared `javascript-swiper.md`） |
| custom element 生命周期（插拔后无残留监听 / timer / observer） | 任何触及 JS 生命周期的改动 |
| 断点覆盖 | 任何视觉改动。**档位由 QA 按 `handoff-schema.md` §5 `BreakpointsCovered` 决定，本文件不列具体断点数值** |
| 多语言长文案 | 触及展示文案、文本容器尺寸、按钮时 |
| A11y 底线 | 触及交互控件、焦点、对比度时（红线 §8.5） |
| 组件写死宽高 / 图片清晰度 / 文案可配置性 | 恒由 QA-Global 覆盖，触及时明确点名 |
| Theme Check | 改了 `.liquid` / schema / `snippets/` / `sections/` / `templates/` / `config/` / `locales/` 任一者 → `ThemeCheckRequired: Yes` |
| admin schema 保存 | 改了 schema 时 |
| build 产物 | 改了 `shopify-common/src` → `BuildRequired: Yes`，待验 build 产物已重新生成且未被手改 |
| 同族发现（本次未修） | 同族扫描分诊出的"另起 ChangeSet"项 |

## 措辞对照（照抄这一列）

**先记语义规则，再看词表**——词表永远列不全，同义改写不能规避禁令：

> 在回复的**任何位置**（含根因、改动清单、顺带发现、结尾寒暄），不得断言本次改动的正确性、稳定性、可用性、验证结果、验收状态，或合并 / 部署 / 发布资格。只能陈述做了什么、为什么、待验证什么。
> 同样禁止**完成度声明**（「开发完成」「实现结束」「不用再改了」）——终结权在 QA。
> 判别法：**这句话如果为真，需要有人执行过验证吗？** 或 **这句话是否暗示"到此为止了"？** 任一为是 → 不能说。


| ❌ 禁止 | ✅ 允许 |
|---|---|
| 修好了 / 已修复完成 | 改动已就位，待 QA |
| 可以上线 / 上线可用 / 可以发布 | 待 `plaud-theme-qa` 验证后由其判定是否可交付 |
| 全部通过 / 回归都过了 / 全绿 | 待验项已列出，尚未执行验证 |
| 没问题了 / 应该没问题 | 需浏览器预览确认，已列入 `BlockingGaps` |
| 已验收 | `QAStatus: NotRun` |
| 我测过了 / 验证无误 | 本 skill 不执行验证 |
| 已具备上线条件 / 生产就绪 / 达到发布标准 | 交付资格由 `plaud-theme-qa` 判定 |
| 可以合并 / 可以部署 / 剩下只需发布 | `NextRequiredSkill: plaud-theme-qa-intake` |
| 风险已清零 / 无需进一步检查 | 待验项已列出，风险由 QA 评估 |

用户催"到底行不行"时，正确回答是：**改动已就位，根因是 X，待 QA 按 QA-A 验证（QA-Global 由 QA 恒执行，不写进 `RequiredQAProfile`）；我无权判定可交付。**
